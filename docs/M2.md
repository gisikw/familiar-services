# M2: scheduler

`familiar-services serve --socket /run/familiar-services/familiar.sock --attention-db PATH --state-dir PATH [--default-target SESSION_ID]` owns Attention and one SQLite scheduler at `STATE_DIR/scheduler.sqlite`.

## Model

An event is `{id, due_at, target, origin, source, priority, type, summary, body, urgency, state, created_at}`. `urgency` is `wake` (the default) or `soft`; `state` is `pending`, `delivered`, or `acked`; a caller-supplied `id` is a permanent deduplication key. A due-now notification and a future wake are identical. Targets are `instance:<Pi session id>` or `spawn:<systemd unit>`; spawn events are retained for M3 and are not delivered. The caller's `FAMILIAR_INSTANCE_ID` becomes `origin`, and target defaults to origin. With neither, the service uses `--default-target`, then the most recently connected instance.

DND is a per-instance scheduler hold. Due wake events remain queued while it is active and release when it clears or expires. Soft events pass through DND because they never interrupt. DND set by Familiar is capped at two hours. Delivery is paced to at most one event per connected instance every 15 seconds, ordered by priority and due time; reconnect redelivery is immediate.

The scheduler also accepts `type: "merge"`. Its body must be JSON containing a non-empty `summary`, `forkSessionId`, `forkSessionFile`, `branchEntryId`, `firstEntryId`, `lastEntryId`, fork-side `mergedAt`, non-negative `turnCount`, and boolean `forkedFurther`. Merge delivery uses the same urgency, pacing, deduplication, redelivery, and acknowledgement rules as every other event.

The socket uses newline-delimited JSON. Short-lived clients use `{op,args}` with `schedule.enqueue`, `schedule.list`, `schedule.cancel`, `dnd.get`, and `dnd.set`. A Pi keeps one connection open, sends `{"op":"hello","args":{"instance":"SESSION_ID"}}`, and receives `{"event": EVENT}`. It injects each event and replies with `schedule.ack`. Delivered-but-unacked events return on reconnect; Pi also deduplicates injected IDs.

Agent operations are `imp schedule --in 30m|--at TIME [--target instance:ID|spawn:UNIT] [--soft] REASON`, `imp schedule list`, `imp schedule cancel ID`, `imp notify [--soft] REASON`, and `imp dnd [on DURATION|off|status]`. Pi sends wake events as turn-triggering messages. It sends soft events with native `deliverAs: "nextTurn"` and acknowledges only after Pi persists the message on the next user turn; a restart while it is merely queued in memory therefore redelivers it.

## Cutover

1. Stop every Pi and all old writers. Back up the state directory, including SQLite `-wal` and `-shm` files.
2. Copy the live file stores only for testing if desired; never test against `/var/lib/kestrel/state/{worklist,wakes}` directly.
3. Run `familiar-services migrate --state-dir PATH --default-target SESSION_ID`. This idempotently imports live `worklist/items/*.json` and `wakes/pending/*.json`; archived and fired records stay historical.
4. Start `serve` with the same state directory and optional default target. Start the new Pi extension and verify its hello, push, injection, and ack.
5. Remove the old file-store writers. Do not dual-write. Rollback requires freezing delivery before restoring the backup.

## Recurrence and scheduled forks

`schedule.enqueue` accepts `rule`, a legible recurrence: an interval (`90m`, `2h`, `1d`; at least 5m) or a wall-clock time on a set of days (`day 06:00`, `weekday 06:00`, `weekend 09:30`, `mon,wed,fri 17:00`). Wall-clock rules run in `FAMILIAR_TZ` (default `America/Chicago`) and stay at local time across DST. Without `due_at`, the first occurrence is the next one after now. The event's id becomes the series id.

Each delivery enqueues the next occurrence in the same transaction, with the deterministic id `SERIES-at-DUEMS`, so a series always has exactly one pending occurrence and a reconnect redelivery can't mint a second. The next occurrence is never at or before the delivery time: if the target was offline, in DND, or the service was down, the missed occurrence fires once on catch-up and the cadence resumes; nothing replays. `schedule.cancel` with any occurrence id, or the series id, stops the series. `schedule.list` with `all: true` lists every target.

`type: "fork"` asks the target instance to fork itself in the background, with the event body as the fork's task. The target's Pi extension runs the same path as `imp fork` once it is idle and takes no model turn for it. Fork events pass DND: starting a background fork interrupts nothing, and the fork's eventual merge obeys DND on its own. A fork event must target an `instance:`.

### Seam for conditional triggers

A condition ("when a new Anthropic model ships") is not a scheduler concept. It belongs to a watcher: anything that notices the condition and calls `schedule.enqueue` (a `fork` to research it, a `push`-sending wake, a soft note) with a stable `id` derived from what it observed (e.g. `model-claude-5-7`), so noticing the same thing twice is idempotent. A watcher can itself be a recurring fork (`every 2h`) that checks, and enqueues only when something is new. The scheduler stays dumb about conditions.
